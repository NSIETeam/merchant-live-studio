# GitHub 自动部署到测试服务器

`main` 推送或在 GitHub Actions 手动运行 CI，先通过现有测试、构建、HTTP 冒烟、生产依赖审计和部署脚本测试，再构建 `/studio/` 前缀的产物并部署到 `8.140.52.117`。拉取请求和开发分支只检查。将一轮功能留在开发分支，统一验收后合并，避免每个修正都发布。

部署使用独立 SSH 密钥及固定主机指纹；仓库 Secrets 为 `STUDIO_DEPLOY_KEY` 和 `STUDIO_KNOWN_HOSTS`。密钥在服务器上强制执行根所有的 `/usr/local/sbin/merchant-live-deploy`，只接受 `deploy <40位提交SHA>`，禁止端口转发、交互终端、任意命令。不会同步 `.env`、登录账号或模型配置。

服务器脚本安装自 `infra/deploy-release.py`，升级脚本需要管理员单独安装，不随普通应用部署替换。首次安装还需给现有 Nginx `/studio/` 代理位置加维护标记判断：`if (-f /opt/merchant-live-studio/maintenance) { return 503; }`。不要在其他业务路由添加此规则。

部署流程：

1. GitHub 检查目标仍为最新主分支，服务器文件锁防止重叠；相同提交健康则幂等返回。
2. 验证压缩包路径和大小，在 SHA 目录安装锁定的生产依赖，禁用安装脚本。
3. 有任何直播间标为直播中就拒绝维护；结束直播后在 Actions 重跑失败的任务。
4. 仅本应用短暂返回维护响应，停止 Live/Agent，并再次检查直播状态；不重启流媒体或其他站点。
5. 备份两个 SQLite 数据库，原子切换链接，启动并核对两服务健康和首页产物。
6. 失败恢复旧链接和数据库后验证；回滚也失败则保留维护状态供人工处置。成功后解除维护。

备份位于 `/opt/merchant-live-studio/backups/auto-*`，提交版本位于 `releases/<SHA>`，非敏感部署记录位于 `automatic-deployment.json`。备份和旧版本不自动清理，需要监测磁盘后人工保留与清理。密钥不能执行手动维护命令。远程脚本异常请通过管理员已有访问方式处理。

自动部署通过只表示测试服务器运行了对应提交，不表示直播资质、支付、真实模型或内容合规已获批准。首次部署及回滚验证记录另行填写，不能以工作流文件存在视为接通。

## 数据库与权限回退保护

新增部署保护：停止服务后用 SQLite backup 生成快照、执行 integrity_check，并记录各数据库 SHA-256（备份目录内 `database-sha256.json`，权限 600）。回退前先校验所有快照，复制后再次校验目标文件，再恢复服务。文件摘要分块计算，不将整库读进内存。

只有新版本验证成功或旧版本连同数据库回退验证成功，才撤掉维护标记。快照损坏、恢复失败或旧服务启动失败时保留维护状态；存在上次遗留维护标记时，下一次自动部署也拒绝继续，须管理员先检查并恢复。不要只删除标记而忽略数据库与权限状态。

9 项部署脚本测试覆盖命令及包校验、正常部署、直播中拒绝切换、数据库模式/停用状态/访问版本回退、损坏快照拒绝恢复、回退启动失败和待恢复状态拦截。测试在临时目录和模拟服务调用上运行，不会向真实服务器部署或触发真实故障。

## 升级期间的旧页面资源

部署脚本将当前版本 `dist/web/assets` 中尚未存在于新产物的文件复制到新版本，因此已打开页面后续请求旧的按需加载 JS/CSS 时仍有对应文件。新产物已有的同名文件不会被旧文件覆盖。当前是扁平资源目录策略，旧资源随版本继续保留，不自动清理；仍需监测磁盘。

部署测试现已放入旧模块、旧样式、新模块和同名资源，验证成功切换后新旧模块共存且新文件不被覆盖，失败回滚或直播中拒绝切换后仍使用原资源。9 项隔离测试通过。此结论来自临时目录下执行部署脚本，不能代替正式服务器升级后旧浏览器会话的端到端验收。

本地直接运行构建会清空并重写 `dist/web`，不经过上述部署步骤；已有浏览器页面可能需重新加载。验收期间应先完成构建再集中检查页面，不在检查尚未载入的功能时持续重建。
