# 录像保留、冻结与删除复核功能卡

主模块为 `live`，协作模块为 `review`，基础文件能力由 `platform/infrastructure` 提供。目标是让管理员对已登记录像建立可追溯保留、在声明期限届满后申请删除，并由另一审核账号复核；任何未解决投诉、申诉或主动保留都会阻止物理删除。

## 用户验收场景

1. 管理员或审核员可在本商家录像片段上建立争议、监管或业务保留，理由和操作者进入不可改写事件记录；另一操作人可释放保留。
2. 未到公开保留期限、直播间仍在直播、存在有效保留或未解决投诉/申诉时，删除申请或执行会明确拒绝。
3. 到期录像由 owner 提交删除申请；生产/团队空间必须由不同 actor 的 reviewer 批准。拒绝保留完整记录，不能改变录像文件。
4. 批准后先把已校验文件移入同文件系统隔离区，再同步复核引用；出现新争议时恢复原文件。完成事件写入后再清理隔离文件；中断后可依据确定路径重试，不把文件缺失误报为成功。
5. 删除完成后登记、申请和审计事件继续保留，列表显示已删除，下载返回 410；其他租户、主播、编辑和分析账号不能读取或操作。

## 接口与权限

- `GET /api/merchant/recordings/:id/retention`：owner/reviewer 读取保留、删除申请、是否到期、引用阻断与可执行状态。
- `POST /api/merchant/recordings/:id/retention/holds`：owner/reviewer 创建主动保留，UUID 幂等键。
- `POST /api/merchant/recordings/:id/retention/holds/:holdId/release`：owner/reviewer 释放，需当前事件版本，创建人与释放人必须不同。
- `POST /api/merchant/recordings/:id/deletion-requests`：owner 创建删除申请，UUID 幂等键；相同键不同内容返回冲突。
- `POST /api/merchant/recordings/:id/deletion-requests/:requestId/review`：reviewer 批准或拒绝，需当前版本；申请人不能复核。批准会执行安全删除并返回最终状态；失败留可重试事件，不伪报完成。

正文沿用 32 KiB 总上限。理由和复核说明为 8–1000 字。列表只返回业务状态和散列，不暴露物理路径或隔离目录。

## 数据与失败恢复

Live 新增 `recording_retention_holds`、`recording_retention_hold_events`、`recording_deletion_requests`、`recording_deletion_events`，全部登记为 `live` 所有。基础记录和事件禁止 UPDATE/DELETE；物理录像删除不删除登记行。Review 仅公开 `hasOpenComplaintDispute(tenant, roomId)`，Live 不读投诉表。schema 从 v22 升至 v23。

文件处理使用录像根目录下权限 0700 的内部隔离区。隔离文件名只由服务端录像 ID 生成。每次移动前后验证字节数和 SHA-256；引用复核失败时恢复原路径；恢复或清理失败写入失败事件并保留文件，由审核员重试。未配置录像目录或留存政策时拒绝申请及批准。

备份仍包含登记和审计数据；完成删除后的媒体不会出现在之后的新备份中。历史备份的到期清理属于部署基础设施，当前流程不宣称同步删除备份副本。

仓库外监管通知、线下纠纷、账务或其他系统引用不会被软件自动发现，运营人员必须先建立主动保留。期限届满也不会批量自动清理。
