# 现有代码模块迁移记录

本次在模块与存储门禁建立后迁移现有实现，保持 HTTP 路径、数据库文件和两个服务的部署入口兼容。后续已在模块边界内增加录像留存和可选微信商家转账链路；通用文件上传仍不在范围内。

## 实现归属

| 所属模块或能力 | 已迁入的实现                                                                            |
| -------------- | --------------------------------------------------------------------------------------- |
| knowledge      | 商品/SKU 与证据版本、房间事实、资料解析和导入回执                                       |
| agent          | 提示词与风格版本、模型适配、任务队列、示例导入、评测、长稿生成、独立 Agent 数据库       |
| content        | 课程与稿件版本、版本比较、保存者记录、生成结果采纳回执                                  |
| review         | 规则预检、本人确认兼容流程、独立审核、审核队列、逐条建议及其处置                        |
| marketing      | 营销周期、目标受众、周期日程约束与课程摘要引用                                          |
| live           | 房间状态、推流与媒体控制、观看心跳、讲稿绑定及历史、现场 Agent 上下文与结果时效校验     |
| engagement     | 活动配置、观看资格、领取申请与状态、提问及互动汇总                                      |
| payments       | 演示预算账本、预留记账、持久出款队列、模拟结算、按商家隔离的微信转账与终态对账          |
| analytics      | 组合直播和互动模块提供的统计结果，不直接联表读取其他模块的数据                          |
| customers      | 当前没有独立的门店客户业务实现，保留注册定义；匿名观看会话继续归 identity，不补造空功能 |
| identity       | 登录、会话撤销、成员权限、认证中间件与请求安全检查                                      |
| infrastructure | 运行配置、通用 HTTP 错误、同步事务控制                                                  |
| adapters       | Agent HTTP 传输、商家侧 Agent/评测接口适配，不加载 Agent 模型或数据库实现               |
| operations     | 健康检查和运行能力说明                                                                  |

后端业务位于 `src/modules/`，公共能力位于 `src/platform/`。`src/composition/studio.ts` 与 `content.ts` 只创建模块、注入接口和注册路由，不执行业务 SQL。

前端按 `agent`、`content`、`review`、`live`、`engagement`、`analytics` 归类；`shell` 管理页面入口和工作台装配，`shared` 保存请求工具和通用组件。一个用户页面可以组合多个模块的能力，目录划分不要求增加用户菜单。

## 数据所有权和事务

[`architecture/table-owners.json`](../architecture/table-owners.json) 登记每张业务表的唯一所有者。现有表名保持兼容，例如 `content_products` 归 knowledge，`content_plans` 归 marketing，`content_room_bindings` 归 live；不能根据历史表名前缀推断所属模块。

SQL 进入所属模块或公共能力的 `persistence/`。跨模块读取改为注入的业务接口：营销模块请求商品所有权和课程摘要，内容模块请求商品版本与审核结果，直播模块请求已绑定内容，统计模块请求各所有者提供的汇总。审核候选查询先取得本租户计划 ID，再查询内容，不扫描其他租户的课程后作为查询结果返回。

业务服务暂时继续使用一个 SQLite 连接。在启动装配阶段将连接注入模块工厂，工厂对外只返回业务操作；连接类型是启动契约，不能通过业务 API、跨模块返回值或前端暴露。运行时只有装配层可创建和连接这些业务模块，其他业务模块不能导入对方工厂。

跨模块同步写入仍在原业务事务内执行。领取过程由 engagement 验证资格和保留领取记录，通过 payments 记账和创建任务；模拟结算由 payments 处理任务，通过 engagement 更新领取状态。共同的同步事务保证失败时一起回滚。嵌套操作使用保存点，不能将异步模型或网络调用放进持锁事务。

Agent 继续拥有独立数据库、配置和进程；其公开运行入口负责数据库关闭，重复关闭共享同一个完成结果。业务服务只通过 Agent HTTP 适配器交互。

## 保留的兼容代码

`src/server/index.ts` 与 `src/agent/index.ts` 保留为可执行入口，使 Docker、systemd、部署包验证及冒烟脚本继续使用原路径。两个入口不再保存业务路由或跨模块 SQL。

`src/server/db.ts` 保留原 v1–v8 数据库初始化和历史迁移，不修改已发布迁移语义，也不移动用户数据库。历史外键与回填在统一启动事务中处理；新增业务功能不得放回该文件。未来新的模式变更先在所属模块 persistence 中定义，并通过明确的启动迁移流程接入。

原先 36 条跨模块依赖豁免缩减为 1 条，仅允许原业务启动入口调用历史数据库初始化。存量文件登记只保留上述三个兼容文件；没有增加豁免或改变原文件所有者。

## 自动检查与验收

`npm run check:architecture` 同时检查模块导入边界和数据库表归属：SQL 执行必须在 persistence 内，静态语句中的读写表必须属于本模块，表必须已登记，无法静态判定的 SQL 会被拒绝。通用事务助手只允许事务控制语句，历史数据库初始化保留明确的单文件兼容例外。

数据库检查是对当前受支持的静态 SQL 形式的检查，不是完整 SQL 解析器或业务授权证明。新增复杂查询需审查并补充检查器覆盖；禁止通过其他执行方式、改表归属或扩大例外绕过检查。租户权限、跨模块事务、真实外部服务和数据恢复仍必须有相应运行时验收。

本次保持原有业务回归测试，并增加：付款队列失败时跨模块回滚、结算回调失败及重试幂等、嵌套事务的内外层回滚、Agent 数据库关闭生命周期，以及表归属检查的负向测试。完整验证使用 `npm run check`；并发冒烟仅访问临时本机进程与数据库，不代表生产容量或真实支付验收。

2026-09-11 本地验证：30 项架构与数据所有权测试、116 项业务测试、类型检查、干净构建和 HTTP 冒烟全部通过。20 个并发观众完成 400 次工作负载请求，工作负载失败为 0；验证领取金额守恒、重复领取幂等，以及停止 Agent 后直播、观看心跳和模拟结算继续运行。临时进程和数据库均已清理。Linux 部署脚本测试由 GitHub CI 执行，本地 Windows 不支持其 `fcntl` 依赖。
