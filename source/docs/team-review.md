# 团队账号与独立审稿

本功能已随 0.6.0 部署并完成测试账号线上验收。它实现账号级职责分离，不验证两个账号背后是否是不同自然人；账号必须由管理员分别交给对应人员。

## 配置

`MERCHANT_CREDENTIALS` 是登录账号到各自访问密钥的映射。`MERCHANT_MEMBERSHIPS` 将成员账号映射到既有管理员的商家空间；未映射账号仍拥有自己原有的空间，不会看到别的商家。

```dotenv
# 下列仅为关系示意，必须为每个账号另行生成独立随机密钥。
MERCHANT_MEMBERSHIPS={"writer":{"merchantId":"owner","role":"editor"},"checker":{"merchantId":"owner","role":"reviewer"},"presenter":{"merchantId":"owner","role":"presenter"},"metrics":{"merchantId":"owner","role":"analyst"}}
```

四个成员和 `owner` 均需出现在凭据映射中。禁止自指、成员互相作为商家、没有凭据的成员和映射为管理员角色。本地演示可以将成员映射到 `demo`，但不得在生产使用演示登录。

修改环境配置后重启 Live 服务。成员的角色/商家映射参与会话凭据版本校验，变更后旧 Cookie 失效；删除账号凭据同样撤销登录。角色来自服务端配置，不能由登录表单或请求体自行声明。现阶段没有在线创建账号或邀请页面。

## 权限

| 角色           | 内容与审核                                             | 直播与运营                                                     |
| -------------- | ------------------------------------------------------ | -------------------------------------------------------------- |
| 管理员 owner   | 管理自己空间；可审核其他账号保存并提交的稿件，不可自审 | 创建房间、密钥轮换、活动与账本                                 |
| 编辑 editor    | 商品/课程/讲稿编辑、提交审核、提示词草稿与试演         | 不可开停播、查看推流密钥或账本、创建红包、发布提示词           |
| 审核 reviewer  | 阅读内容及依据，批准或退回待审版本                     | 不可改正文、绑定、开停播或读取推流密钥与账本                   |
| 主播 presenter | 阅读内容并绑定已批准版本                               | 开停播、读取当前推流配置、现场建议与反馈；不可轮换密钥或发红包 |
| 复盘 analyst   | 不可读取商品私有资料或修改内容                         | 只读房间、观看分析、活动记录与账本；不可读取推流密钥           |

权限在 `/api/merchant/*` 统一检查，资源仍按商家归属复核。未授权的写请求返回 403。审核页正文与绑定按钮也按角色禁用；页面只是辅助，接口权限不依赖按钮状态。

## 流程与不可变记录

1. 保存新版本时记录真实登录账号，作为该版本保存者。旧版本不补造保存者，需先重新保存才能送独立审核。
2. 编辑或管理员提交最新版本，必须没有过期依据和阻断项；记录提交账号、时间及说明。
3. 另一审核/管理员账号阅读全文、版本对照及依据，选择批准或退回。保存者和提交者都不能审核该版本。出现更新稿件后，不能再批准较旧的待审版本。
4. 每个版本的决定不可覆盖。相同决定重试保持幂等；退回后修改并保存新版本，再重新提交。批准从决定中生成 `independent_review` 定稿身份。
5. 主播绑定获批版本；绑定历史保存主播登录账号，而不是统一记为商家编号。证据改变时，旧批准作为历史保留，但稿件和绑定失效。

生产环境，或为该商家配置了任一团队成员时，自动要求独立审核。旧版本人确认不能通过新绑定检查，旧绑定读取会提示需复核。升级前应先配置编辑和审核账号，并安排重新保存、审核及绑定；不要将历史自确认伪装成独立批准。本地无团队的单人演示保留自确认，进入独立审核后不能再走自确认路径。

审核记录、提交记录和保存者表均在迁移 v6 中建立，记录不可修改或删除。它们与内容保存在同一数据库，Agent 停止不影响本流程。集中待办和逐条修改建议已有开发增量；批准撤回和真实人员身份核验尚未完成。

## 接口

路径前缀为 `/api/merchant/content`，始终校验商家身份。

| 方法 | 路径                                   | 请求                                                                                               |
| ---- | -------------------------------------- | -------------------------------------------------------------------------------------------------- |
| GET  | `/courses/:id/scripts/:version/review` | 返回保存者、提交与决定；未知旧保存者为 null                                                        |
| POST | `/courses/:id/scripts/:version/submit` | `{ "note": "提交说明" }`                                                                           |
| POST | `/courses/:id/scripts/:version/review` | `{ "decision": "approved", "note": "审核意见", "acknowledged": true }`；退回用 `changes_requested` |

`/api/auth/me` 和正常账号登录返回 `merchantId`、`actorId`、`memberRole`、`requiresIndependentReview`。定稿仍不等于法律结论，审核人员需要核查真实材料和实际表达语境。

## 集中待审工作台

管理员和审核账号可在「商品与课程」顶部展开「待审核工作台」，查看本商家各课程最新、尚无审核决定的已提交版本。打开条目后展示全文、引用依据、逐段规则提示，并沿用独立审核权限作出批准或退回决定。每次操作仍由服务端重新校验最新版本和证据状态。

`GET /api/merchant/content/review-queue?limit=20&after=<courseId>` 返回 `items` 和 `nextAfter`；limit 为 1–50，按课程 ID 使用游标翻页，避免其他审核人处理前页后导致后页跳项。新提交可刷新首页查看。旧提交被新稿替代后不再进入待审列表，历史记录仍保留在课程版本中。

`GET /api/merchant/content/courses/:id/scripts/:version` 返回指定版本的讲稿快照与当前失效状态，受商家隔离和成员权限保护。该入口不是公开观众接口。

## 逐条修改建议（迁移 v7，0.6 已部署）

审核/管理员账号可对最新已提交、未批准稿件的具体段落提出替换正文和理由；保存者与提交者不能自行提出独立建议。每版最多 100 条。编辑/管理员逐条填写理由并采纳或拒绝。正文替换不改变段落类型和引用依据，变更事实引用应在编辑器中重新核对。

采纳将基于当前最新稿创建新版本，重新运行内容检查，并在同一事务写入处置记录。原文和其他段落保持原样；若目标段落已变化或删除、证据或规则已过期，拒绝覆盖。超过全稿限制时全部回滚。新版本必须重新提交独立审核，不继承旧稿批准。原版本里的建议显示新稿版本、处置人、时间和理由。拒绝只记录决定，不创建版本；决定不可改写。当前版本仍有未处置建议时不能批准。

接口：

- `GET /api/merchant/content/courses/:id/scripts/:version/suggestions`：此版建议与处置记录，受商家隔离保护。
- `POST` 同路径：`{id, paragraphId, replacement, reason}`；id 为调用方生成的 UUID，同编号同内容可安全重试，冲突返回 409。
- `POST /api/merchant/content/suggestions/:id/resolve`：`{decision: "accepted" | "rejected", note}`，返回 `resultVersion`（拒绝为 null）。同账号同决定同理由重试不会重复写入版本，不同处置返回 409。

仅替换正文，尚无批量建议操作；多条建议若针对同一段落，采纳其中一条后，其他旧建议需重新核对。旧版建议可从版本选择器查看和处理。角色配置仍由服务器环境管理。
