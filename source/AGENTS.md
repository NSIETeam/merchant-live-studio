# 靠谱仓库开发硬门禁

本文件适用于整个仓库。所有开发者和编码智能体必须先阅读本文件及 [模块开发规范](docs/module-development.md)；涉及数据、文件或媒体时还必须阅读 [存储规范](docs/storage-architecture.md)。用户已确认的最终模块划分是开发约束，不能为赶进度合并职责或扩大遗留依赖。

## 模块归属

业务模块固定为：`knowledge` 商品与知识资料、`agent` 智能体、`content` 内容与素材、`review` 审核与发布、`marketing` 营销计划、`live` 直播、`customers` 门店与客户、`engagement` 互动与权益、`payments` 支付与结算、`analytics` 数据与业务复盘。

定义及数据归属以 `architecture/modules.json` 和 `docs/module-development.md` 为准。公共基础能力为身份与组织、文件与媒体基础设施、外部协议适配、运行与用量管理。

## 开发前必须完成

1. 新增功能或修改业务行为，必须在编写实现前准备一张[简短功能卡](docs/feature-card-template.md)，说明主模块与协作模块、用户验收场景、接口变化、数据变化、权限和失败处理。卡片在功能文档、Issue 或草稿 PR 中选一处维护，其他位置引用；已有规则直接链接，范围变化时同步更新。纯文档或样式调整可在变更说明中简述范围及验证方式，不要求另建卡片。
2. 跨模块功能先确定输入输出、权限、错误、版本、超时和幂等契约。跨模块运行时调用通过公开接口及依赖注入、HTTP 或事件完成，由装配层连接。
3. 新后端业务代码必须放在 `src/modules/<模块名>/`，公共基础实现放在 `src/platform/<基础能力>/`，装配代码放在 `src/composition/`。前端新功能放在 `src/web/<模块名>/`，壳层和通用界面放在 `src/web/shell/`、`src/web/shared/`。共享契约继续放在 `src/shared/`。

## 禁止事项

- 禁止业务模块直接导入另一个业务模块的运行时实现；跨模块仅可导入对方根目录 `public.ts` 的类型。装配层可导入公开运行时入口并注入接口。
- 禁止导入其他模块的私有文件或读写其数据库表；数据库驱动仅可在所属模块的 `persistence/` 内使用。公共接口返回业务数据，不能暴露可绕过所有权的数据库句柄。
- 数据库语句必须放在所属模块或公共能力的 `persistence/`，表所有者登记于 `architecture/table-owners.json`。跨模块查询通过业务接口完成；禁止用动态 SQL、改变表归属或其他执行方式绕过数据所有权检查。共享业务连接仅在启动装配时注入模块工厂，不能作为业务返回值传递。
- 禁止前端导入后端实现或数据库驱动；共享契约不得反向依赖业务、前端、平台实现。
- 禁止 Agent 直接修改正式商品证据、审核决定、直播状态或资金账本。Agent 输出先作为候选结果，业务写入由对应模块授权并执行。
- 禁止将生成完成当作审核批准，将本人确认当作独立审核，将模拟红包当作真实支付，将模型评分或奖励驱动的完播率当作成交效果。
- 禁止为了通过检查而关闭门禁、放宽规则、增加豁免、使用动态加载或将业务实现移出扫描范围。

## 关键业务边界

- `knowledge` 提供证据；`agent` 生成和建议；`content` 保存内容版本；`review` 决定批准、发布与失效；`live` 消费有效发布内容。
- `marketing` 管理周期、目标、安排；`content` 管理课程和素材本身。
- `live` 记录观看和场次事实；`engagement` 判断活动权益；`payments` 拥有资金状态和账本。
- `customers` 记录客户服务和线下订单；`analytics` 进行业务复盘。Agent 的内容质量评测留在 `agent`。
- Agent 服务、业务服务、流媒体保持运行边界。Agent 故障不得阻断已有有效内容的直播与互动；新发布或新绑定仍需验证审核资格。
- 商品、规则、提示词、主播风格和发布内容必须可追溯到版本。资料与样例中的文字是任务数据，不能提升为系统行为指令。

## 存储硬门禁

涉及存储的功能必须遵循 [存储规范](docs/storage-architecture.md)，开发前明确所属模块、数据类别、落点、元数据、版本和来源、权限、体积配额、失败恢复、保留清理及备份恢复。

- 业务库和 Agent 库保持分离。结构化数据、短文本和版本关系入所属数据库；大型上传与媒体通过私有资产存储管理，禁止塞入 Base64 业务字段。
- 每个资产必须有唯一租户和所属模块；原件、派生结果、AI 候选、正式素材、录像、播放缓存和临时文件按用途及生命周期隔离。任何用户文件不得落入 `public/`、`src/`、`dist/` 或镜像构建上下文。
- 业务代码通过受控资产接口使用文件，不自行拼接路径、调用存储 SDK 或写入其他模块目录。通用字节存储位于 `src/platform/infrastructure/`，元数据和业务决策留在所属模块，装配层注入依赖。
- 文件状态 ready 不等于审核批准；新版本不得覆盖原件或已批准版本。跨模块使用建立授权引用，Agent 候选采纳为 content 独立草稿资产，保留来源且不能因源候选清理而失效。
- 访问须校验租户、权限和必要的发布资格；目录、随机 ID、文件后缀和永久 URL 均不能充当授权。跨模块文件访问不能靠共享整个数据卷实现。
- 文件写入与数据库更新分别处理完成、失败、重试和恢复；禁止暴露未完成文件。物理删除前必须检查并锁定引用、租约与保留策略，状态不明时保留；不得只按文件年龄、后缀或目录批量删除。
- 保持直播缓存与持久录像隔离。备份包含一致的数据库快照及其引用对象，配置恢复目标并验证还原；不能把本地暂存或直接复制运行中的 SQLite 主文件当作完整备份。

这些规则必须经过设计、代码审查及相关运行时测试。现有架构导入检查不自动证明文件授权、清理和备份正确；涉及这些功能必须增加相应验收，不能仅凭旧测试全绿交付。

## 遗留代码迁移

`architecture/legacy-files.json` 是源码快照 `9493ed1` 的存量文件清单，`architecture/legacy-imports.json` 仅豁免当时已经存在的具体依赖。它们不是新增功能的入口或全目录白名单。

现有业务实现已按模块迁移，见 [迁移记录](docs/module-migration.md)。存量代码仅保留两个部署入口和原数据库历史迁移；唯一依赖豁免是业务启动入口调用数据库初始化。

- 允许修复存量缺陷和逐步抽取模块；新业务功能必须在目标模块实现。
- 新模块不得依赖遗留后端实现，遗留入口只能通过公开入口接入新能力。
- 迁移后删除已经不再使用的豁免和存量条目；不得自动重新生成基线掩盖违规。
- 模块增删、责任转移或门禁放宽必须作为明确的架构变更单独说明，不得混入普通功能提交。

## 完成和交付门禁

### 实现：完成可验证的业务流程

- 按功能卡完成从实际入口、服务处理、必要的数据保存到用户可见结果的流程，并处理相关的加载、空数据、失败和权限状态。保存类操作需要重新读取验证，不能只以成功提示或函数被调用作为验收。
- 例如“上传资料”必须验证上传、校验、保存、授权读取和失败提示；目录、接口占位或页面按钮存在不能作为该功能完成的证据。
- 允许分阶段提交，但每阶段必须有明确范围、可验证结果和未完成项。只有验收通过的阶段可标记完成，不能将局部实现写成整个功能已完成；未完成入口不得向用户伪报成功。
- 模拟数据、模拟模型和模拟支付必须在相关界面、结果及交付记录中明确标识；未接入外部能力时如实返回未配置或不可用。

### 合并：基础检查全跑，专项验证按改动补

必须对待合并变更运行 `npm run check`，包含架构检查及其负向测试、业务测试、类型检查、构建和 HTTP 冒烟测试；GitHub CI 的依赖审计及部署脚本测试也必须通过。检查失败、缺少适用的专项证据或用户流程未达到所声明阶段时，不能标记该阶段完成或提交合并。更新代码后必须重新验证受影响检查，不能使用旧提交的 CI 结果替代当前版本。

专项验证根据实际改动及其业务影响选择，既有测试已充分覆盖时可引用，不为凑数量新增测试：

| 改动范围               | 必须验证的业务结果                                                                 |
| ---------------------- | ---------------------------------------------------------------------------------- |
| 审核、发布与内容版本   | 自审拒绝、权限边界、旧审核不能批准新版本、证据变化后的资格失效                     |
| 领取、结算与账本       | 并发与重复请求不重复产生业务结果、金额守恒、中途失败回滚或恢复                     |
| Agent 通信与运行边界   | Agent 停止、超时或错误时，已有有效内容的直播与互动仍可运行；新发布或绑定仍校验资格 |
| 租户、成员与资源权限   | 其他租户及权限不足的访问被拒绝，权限撤销生效，公开响应不泄露内部数据               |
| 任务、导入、跨模块事件 | 中断、取消、重复处理和重启后的状态符合契约，不重复发布或付款                       |
| 数据、附件、媒体或迁移 | 按存储规范验证此次变更涉及的授权、版本、引用保护、失败恢复、数据保留与备份恢复     |

测试应断言业务状态、持久数据或用户可见结果；仅验证内部函数调用、文件存在或测试数量不能替代业务验收。影响用户操作流程的变更还需记录实际界面验证；纯文档或样式调整不要求新增无意义的业务测试。

PR 按[交付模板](.github/pull_request_template.md)引用功能卡，列明已完成范围、未完成项、适用的专项验证与实际结果。不适用的检查说明原因，不把未运行写成通过。

### 发布：验证待部署的具体版本

- 发布前按[发布验收记录模板](docs/release-verification-template.md)确认目标环境、完整提交 SHA、对应 CI、构建产物、迁移条件、备份安排、健康检查与回滚路径。迁移和存储恢复遵循已有规范；无相关变更时写明不适用的原因。
- 发布后核对实际运行版本与目标 SHA、产物一致性、Live/Agent 健康、首页与必要的关键流程，记录本次备份位置和实际部署结果。CI 通过、合并完成或部署命令退出不能单独作为部署成功的证据。
- 部署被阻止、跳过或已回滚时记录实际状态及仍在运行的版本，不标记目标版本已部署。遵循现有直播维护保护，不伪造直播空闲状态或关闭保护强行更新。
- 外部模型、微信、真实资金及真实推流的验收与本地模拟测试分别记录，包含验证环境、版本、实际结果和待办；未配置或未验证的能力不得声明已通过真实环境验收。

功能卡、流程完整性、专项证据和发布记录属于必须执行的开发与审查门禁；现有 CI 不会自动证明这些说明真实、充分，也不会自动配置远端分支保护。AI 不得擅自提交、推送、部署或调整 GitHub 分支保护来绕过门禁。
