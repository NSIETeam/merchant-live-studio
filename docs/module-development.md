# 模块开发规范与硬门禁

本规范将已确认的最终模块划分固化为仓库开发约束。它覆盖最终产品形态，具体实现按完整用户流程分期推进。十个业务模块不是十个微服务，也不是十个必须逐一打开的菜单。

## 模块与数据所有权

机器可读注册表为 [`architecture/modules.json`](../architecture/modules.json)。模块拥有自己的业务数据和变更规则，协作方通过接口使用能力。

| 模块       | 负责                                           | 对外能力与边界                              |
| ---------- | ---------------------------------------------- | ------------------------------------------- |
| knowledge  | 商品/SKU、资质、资料、规则来源与证据版本       | 提供已核实资料和版本；AI 提取的事实先待审   |
| agent      | 提示词、风格、检索、生成、审稿建议、任务和评测 | 返回候选内容和问题依据，不直接改业务状态    |
| content    | 课程、讲稿、多种形式的素材、编辑及版本         | 接收任务结果为草稿，保存不可变内容版本      |
| review     | 审核、建议、批准退回、发布、撤回失效           | 决定特定版本能否使用；AI 检查不替代独立审核 |
| marketing  | 周期、受众、目标、主题、日程和门店动作         | 引用课程和内容，不重复维护稿件正文          |
| live       | 房间、场次、流媒体、提词、上屏、录制、观看     | 使用有效发布包，记录每一独立场次            |
| customers  | 客户与员工服务关系、到店、体验、线下订单       | 保留来源、纠错及未匹配记录，不重复实现认证  |
| engagement | 提问、签到、积分、礼品、红包资格与申请         | 判断权益，向 payments 提交经授权的结算请求  |
| payments   | 资金、出款、回调、冲正、账本、对账             | 维护真实资金状态，现金与积分、礼品分别记录  |
| analytics  | 观看、内容、风格、周期、门店、订单与成本分析   | 提供业务结果；与 agent 的内容质量评测区分   |

公共能力为 `identity`（组织、账号、角色、资源授权）、`infrastructure`（文件、媒体和运行基础）、`adapters`（外部协议适配）、`operations`（配置、审计、用量与运行管理）。模型适配、密钥与执行由 Agent 管理，支付适配的业务决策由 payments 管理。

## Agent 内部能力

Agent 按提示词与任务模板、主播与品牌风格、上下文准备、任务编排、模型与工具适配、输出检查与评测划分内部代码。样例保留授权来源，提示词与风格按版本评测和发布；记录反馈不等于自动训练模型。长稿及媒体任务与直播现场建议使用独立调度预算。

## 目录与装配

为兼容现有 TypeScript/Vite 编译路径，新结构位于 `src/` 内，而非立即迁移为多包工程：

```text
src/modules/<module>/public.ts       公开类型、工厂和业务接口
src/modules/<module>/...             模块内部实现
src/modules/<module>/persistence/    所属模块的数据访问
src/platform/<capability>/public.ts  公共基础能力入口
src/platform/<capability>/...        基础能力内部实现
src/composition/                     应用装配与适配接口注入
src/shared/                          类型、事件、DTO、校验和纯契约辅助
src/web/<module>/                    前端功能
src/web/shell/                       页面及角色入口装配
src/web/shared/                      通用前端能力
```

业务模块内部可调用私有实现。另一个模块仅可从其根 `public.ts` 导入类型；运行时实现由 `composition` 注入，或通过 HTTP/事件契约提供。基础能力只能依赖其他基础能力的公开入口和共享契约，不能反向依赖业务。前端仅使用前端代码、共享契约和业务 HTTP API。

公开入口不得重新导出可跨模块执行 SQL 的数据库句柄。即使起步共用业务数据库，每张表也必须有唯一所属模块，跨模块读取同样经过接口。Agent 数据库和业务数据库继续分离。

## 存储与文件所有权

文件分类、物理落点、资产元数据、版本、访问、清理与备份必须遵循 [平台存储规范](storage-architecture.md)。文件与媒体属于已有模块的业务资产，通用字节存储由 infrastructure 提供，不新增一个接管所有业务数据的“文件模块”。

原始资料、派生结果、Agent 候选、内容素材、直播录像与缓存分别管理；每个资产只有一个所属模块。模块通过受控接口和固定版本引用协作，不能直接读取对方磁盘目录。Agent 候选采纳后由 content 独立保存，review 管理发布资格，live 使用经授权的确定版本。涉及存储的功能必须给出失败恢复、引用保护、清理和备份验收。

## 接口与用户流程

接口必须定义权限、租户与操作者来源、输入输出、版本、失败、超时和幂等规则。长任务提交后查询结果，支持取消与恢复；跨模块状态通知需要持久化和重复消费处理。装配层只连接接口，不实现商品、审核、权益等业务规则。

典型流程为：marketing 建立计划 → knowledge 提供证据快照 → agent 生成候选 → content 保存草稿 → review 独立批准并形成发布包 → live 播出或 customers 使用门店素材 → engagement/payments 执行互动结算 → analytics 复盘。

发布包固定内容、素材、证据及审核记录，并保留生成任务、提示词和风格版本的追溯引用。内容修改产生新版本；证据变化触发复核。Agent 离线不影响已有有效内容的直播和互动；新发布或绑定不得跳过审核状态校验。运行中的内容缓存有效期、撤回处理和故障恢复必须在相关功能验收中明确。

## 自动检查

运行 `npm run check:architecture`，或完整运行 `npm run check`。GitHub CI 的 `check` 作业通过后者执行本门禁，失败返回非零退出码。

机器检查覆盖：

- 新源码是否归属注册模块、基础能力、共享契约、前端或装配层。
- 业务模块间的直接运行时依赖、跨模块私有导入、基础能力反向依赖及前后端越界。
- 静态导入、重导出、类型导入、字面量动态导入和 require；非字面量加载及自建加载器被拒绝。
- TypeScript 路径别名及实际解析路径，禁止越出受管源码目录和符号链接。
- 数据库驱动是否局限于模块 persistence；Agent 与遗留业务服务是否保持实现隔离。
- 遗留依赖是否精确命中登记项，迁移后是否留下无效豁免。
- CI 对比 PR 的目标分支提交或 push 前提交，拒绝新增遗留文件、修改遗留归属、增加依赖豁免；首次引入基线单独识别。可用完整提交 SHA 设置 `ARCHITECTURE_BASE_REF` 在本地执行同样比较，无法读取指定提交时失败。

自动检查不能证明 HTTP 调用的业务语义、每条 SQL 的数据所有权、真实支付或模型效果正确。这些仍是必须履行的审查和运行时验收门禁，不能因为导入检查通过而省略。

## 存量迁移

基于原源码快照建立 `architecture/legacy-files.json` 和 `architecture/legacy-imports.json`。存量清单逐文件登记归属与迁移说明，依赖豁免精确到来源、目标、类型或运行时形式及导入符号，不按整个目录放行。新模块不得反向依赖遗留后端。

`src/server/content.ts` 中商品、营销计划、稿件和审核协作逐步移往相应模块。`src/server/app.ts` 中直播、身份、互动、资金和分析逐步分离。新业务功能必须进入新模块，遗留文件只保留必要的接线、缺陷修复及迁移操作。

迁移时删除相应旧文件或豁免；不提供自动更新基线的生产命令。不得为通过检查增加豁免或修改检测器。确需改变边界时，须作为明确架构变更说明理由、影响和验证，遵循用户的架构决定。

## 完成标准和合并要求

每项功能提交说明必须包含：主模块与协作模块、数据所有权、公开契约、权限和故障行为、关键用户流程及验证结果。涉及存储时还需说明存储规范要求的分类、版本、引用、配额、保留和恢复。模板见 `.github/pull_request_template.md`。`npm run check` 必须全绿。

跨租户、独立审核、资金、任务重试取消和事件消费等高影响变更必须有对应边界验证。纯文档和样式修改无需为凑数量新增业务测试。模拟、真实模型、真实渠道、实际推流及业务试点分别报告完成情况。

仓库脚本和 CI 能产生失败检查；GitHub 阻止合并还需要远端分支规则将 `check` 设为必过并限制绕过。提交本规范不会自动修改 GitHub 分支保护，也不能防止有管理权限的人删除检查。不得宣称本地检查等于远端保护已配置。
