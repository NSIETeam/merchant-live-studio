# 功能卡：微信商家转账 APIv3 适配器

## 实现前填写

- **所属模块**：`payments` 模块提供微信商家转账的纯传输与密码学适配器；身份、领取资格和账本仍由各自模块负责。适配器不访问业务数据库，也不从浏览器接收 OpenID。
- **用户验收场景**：后续取得已获批微信支付商户配置后，支付 worker 可使用服务器已核验的收款身份发起转账、按原商户单号查询未知结果，并验签解密终态通知。配置缺失时仍明确不可用，不能把接口代码存在显示为到账。
- **接口变化**：保留 `PaymentProvider` 的发起、查询、通知验签三项契约；`WeChatPaymentProvider` 增加显式配置和可替换 HTTP 传输。业务接通阶段再把它接到授权、领取、任务和查询接口。
- **数据变化**：Live schema 由 v24 逐步升至 v27。`payments` 新增 `payment_transfers`、不可改写的 `payment_transfer_events` 和 `payment_notification_receipts`；`identity` 新增不可改写的 `wechat_recipient_authorization_events`；活动保存支付模式快照。OpenID 仅在 OAuth 后短时保存在进程内，观众明确授权后以 AES-256-GCM 密文保存，并另存按商家隔离的 keyed digest；支付模块只保存 digest，不保存 OpenID 明文。
- **权限**：调用者必须提供与配置租户相同的内部商家 ID、服务端核验的 OpenID、唯一且符合微信规则的商户单号和整数分金额。适配器固定使用服务器配置的商户号、场景、备注、报备字段、通知地址和密钥，不接受观众覆盖。
- **失败处理**：请求和响应均有 8 秒/64 KiB 边界；所有微信应答及通知必须用配置序列号对应公钥验签，签名探测流量被拒绝。通知仅接受商家转账终态，使用 APIv3 密钥进行 AES-256-GCM 解密并核对商户号。创建请求失败或结果未知时不换单重付，应查询原单。

## 业务接通阶段

- **主模块与协作模块**：`payments` 拥有转账单、通知、对账状态和资金账本；`identity` 只在微信 OAuth 成功后短时暂存 OpenID，并在观众明确授权后提供按商家隔离的加密收款身份；`engagement` 只提交包含活动、领取、观众、商家和金额的不可歧义结算请求。`composition` 负责注入这些公开接口。
- **用户验收场景**：微信观众进入某商家直播间后，可看到真实红包是否已配置；完成 OAuth 后仍需在观众页明确同意将本次微信身份用于该商家的红包收款。授权成功后领取才会产生一张持久转账单。网络未知、进程重启和重复领取均查询同一商户单号。观众可查看本人领取的转账状态；商家账本可区分模拟结算和微信转账状态。
- **配置与租户**：真实模式只读取服务器上的私有配置文件，按内部 `merchantId` 建立供应方注册表，并按 `Wechatpay-Serial` 路由通知。未配置的商家不可创建真实红包或领取。配置不从商家或观众请求中覆盖；默认和现有生产环境继续使用 `simulation`。
- **接口变化**：新增观众收款授权状态、确认和撤回接口；领取响应返回实际支付模式和转账状态；新增本人转账状态读取；微信通知端点在真实模式下验签、解密、核对租户/金额/收款身份后幂等入库，在模拟模式继续返回未配置。
- **数据变化**：在现有 schema v26 基础上增加资金模式快照及幂等账本归集所需字段或事件；不修改既有不可变事件。终态到账与失败返还通过确定性账本 ID 重放安全地归集，任何通知都不能直接改 `engagement` 拥有的领取事实。
- **权限与隐私**：收款授权接口只接受有效观众会话和实际直播间；状态查询只能读取当前观众自己的领取。回调不得绕过微信签名、平台序列号、商户号、原商户单号、金额和 OpenID 全部匹配。公开响应不包含 OpenID、密文、摘要、证书、上游错误正文或内部配置。
- **失败与恢复**：领取事务必须同时完成活动扣减、领取记录、资金账本预留和转账排队，否则整体回滚。转账 worker 在外部调用前持久认领，创建结果未知后只查原单；终态账本归集可重复运行。授权撤回阻止新领取，不篡改已产生的付款义务。

## 随实现补充证据

- **协议依据**：发起端点、参数、单号与状态按微信支付当前[发起转账](https://pay.wechatpay.cn/doc/v3/merchant/4012716434)说明；通知验签、终态、幂等和 AES-256-GCM 解密按[商家转账回调](https://pay.wechatpay.cn/doc/v3/merchant/4012712115)说明；请求与应答均执行 [APIv3 签名验签](https://pay.wechatpay.cn/doc/v3/merchant/4012365342)。
- **专项验证**：使用两组本地临时 RSA 密钥和 AES-256-GCM 合成通知验证真实密码学路径，覆盖请求规范串与签名、固定参数、应答签名、原单查询、终态解密、商户匹配、坏签名、错单号、非终态和缺失配置。状态存储专项覆盖一领取一单、崩溃后查原单状态、单号/收款人/金额不可变、终态不可回退、通知幂等与同 ID 异文拒绝；身份保险库专项覆盖短时暂存、明确授权、租户隔离、密文防调包、撤回和数据库无 OpenID 明文。
- **阶段状态**：传输、状态存储、收款身份保险库、OAuth 暂存、观众授权界面、持久 worker、用户确认参数和终态账本已经接通，默认仍为 `simulation`。当前 registry 支持内部多个普通商户配置；服务商/子商户模式需根据最终合同另行实现。真正启用还需要配置获批商户证书与平台公钥、备案域名，完成商户产品/场景审批和微信小额实测。
- **用户确认依据**：H5 通过微信 JS-SDK 的 [`requestMerchantTransfer`](https://pay.wechatpay.cn/doc/v3/merchant/4012716430) 拉起确认页；返回 `ok` 只表示页面成功展示，最终结果仍由验签回调或服务端查询确认。
- **完整验证**：以本次提交对应的 CI `check` 结果为准；本地覆盖真实密码学适配、端到端授权与领取、重复通知、终态归账、类型检查、生产构建和 HTTP 冒烟。
