# 签到、积分与礼品（本地开发，未统一部署）

## 操作方式

管理员在“互动活动”中配置每次签到积分、本场累计观看秒数、每日名额及是否开放。按上海时区自然日计算，每个直播间、每个观众会话每天一次。规则变更保留版本；已领取积分不随新规则改变。同一商家的积分可用于该商家的礼品。

观众从底部“活动”进入签到与积分。必须处于正在计时的直播观看状态，且满足本场累计时长；昨日积累的本场时长可以延续，但每天领取时仍需新的有效心跳。每日名额限制实际发放次数。已经签到的请求重试返回原记录。

商家创建礼品时填写名称、领取说明、兑换积分与可用库存，并主动上架。可用库存不含已预留的礼品。编辑时校验旧版本与旧库存，库存被另一笔兑换改变时拒绝覆盖。

观众确认兑换后，同一数据库事务预留一件库存、扣除积分并保存领取码。礼品名称和兑换价格固定在该记录，后续调价不影响旧兑换。待领取的兑换可以取消，取消原子返还积分和库存；已领取不能再取消。没有自动物流、自动发货或资金转账。

商家拿到观众提供的领取码并实际交付后，在记录中填写交付说明并核销。商家列表不显示领取码，观众自己的记录可见。操作历史保留办理人员、说明和时间；重复同一操作不会重复扣分或退款。

## 数据与安全边界

- 当前匿名会话不是实名认证。多浏览器、多设备可能重复领取；每日限额和库存只能限制损失范围，不能替代正式身份与风控。匿名会话过期或被清除后，尚无自助账户恢复。
- 积分没有现金价值，不可提现，和红包及支付账本分开。尚无积分购买、转赠、人工改余额或现金兑换接口。
- 积分分录、签到、规则版本、礼品编辑历史、兑换事件不可直接修改或删除；余额由分录汇总。兑换取消产生补偿分录，不抹去原扣分。
- 管理员可配置与核销；分析员只读；其他商家角色无权读取兑换记录。观众仅能查看/取消自己在对应商家的兑换。
- 每日签到事务与兑换事务在 SQLite 中串行提交，保障单实例库存与余额一致性。并发测试是本地正确性验证，不是万人容量证明。
- 观众展示最近 100 条积分和兑换记录，商家领取列表可继续翻页。暂未实现观众全部历史导出、过期自动返还、物流追踪、已交付退货、人工纠错积分或核销撤销；若需退货应新增审核与反向业务事件，不能篡改账本。

## 服务接口

商家：`/api/merchant/engagement/rooms/:id` GET/POST 规则与当日签到数；`gifts` GET/POST；`gifts/:id` PATCH；`redemptions` GET 分页；`redemptions/:id/history` GET；`redemptions/:id/fulfill` 和 `cancel` POST。

观众：`/api/viewer/rooms/:id/engagement` GET 状态、余额、礼品与最近记录；`checkin` POST；`redeem` POST（giftId 与 idempotencyKey）；`redemptions/:redemptionId/cancel` POST。

积分兑换必须复用同一请求编号来重试不确定的网络结果。同一编号换礼品返回冲突。所有 POST 均采用 JSON 请求体，空参数用 `{}`。

数据库迁移 v10 创建独立 engagement 表。当前线上版本保持不变，统一部署时需按既有备份与回滚流程升级。

## 验收

自动测试包含签到重试、名额、观看门槛、跨日心跳、库存竞争、领取码拒绝、取消补偿、核销终态、跨商家/跨观众隔离、角色权限、库存编辑冲突、冻结兑换价格和数据库重开。浏览器联测与真实商家使用结果另行记录；自动测试不证明实物交付或实名防刷。

本地浏览器已验证规则保存、礼品上架、观众余额/礼品显示及未播放时禁止签到。本轮未接视频信号，完整观看签到、兑换和核销的浏览器流程仍待整体联测；对应状态转换与隔离已在接口测试中验证。
